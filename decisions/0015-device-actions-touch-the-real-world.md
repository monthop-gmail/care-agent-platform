# ADR-0015: การกระทำต่ออุปกรณ์เป็น capability ชนิดใหม่ — หยุดต้องไม่รอใคร และเปิดต่อต้องไม่ง่ายกว่าหยุด

**Status:** Accepted (2026-09-27)
**Depends on:** [ADR-0006](0006-ai-has-no-medical-authority.md) · [ADR-0007](0007-consent-and-data-access.md) · [ADR-0014](0014-presentation-intent-is-a-request-not-a-command.md)
**อ้าง:** [agent-platform ADR-0029](https://github.com/monthop-gmail/agent-platform/blob/main/decisions/0029-the-cost-of-not-acting.md) กฎ 1a/1b ที่ repo นี้เป็นผู้ผลิตรายแรก
**ตอบ:** `task-7538109a` ADR B

## Context

`policies/care-authority-map.yaml` มี 29 capability และ **ทุกตัวเป็น notify · record · propose**
ไม่มีตัวไหนเปลี่ยนสภาพแวดล้อมของผู้ป่วย

การหยุดวิดีโอที่ผู้ป่วยกำลังดูเพื่อเตือนกินยา จึงไม่ใช่ capability ที่เพิ่มต่อจากของเดิม
มันเป็น **ชนิดใหม่** — action แรกของระบบนี้ที่ผลออกไปถึงโลกจริงโดยไม่ผ่านการตัดสินใจของคน
ที่อยู่ตรงนั้น

> ความต่างไม่ใช่ระดับความเสี่ยง แต่คือ **ใครเป็นคนลงมือ** · การเตือนคือการบอก
> คนที่รับยังเลือกได้ · การหยุดจอคือการทำ และคนที่ถูกทำไม่ได้เลือก

## Decision

### 1. ประกาศเป็นชนิด `device action` และแยก capability ต่อการกระทำเสมอ

```yaml
media.playback.pause:    { action_risk: critical, override_authority: notify, requires_full_audit: true }
media.playback.cancel:   { action_risk: critical, override_authority: notify, requires_full_audit: true }
media.playback.resume:   { action_risk: medium }
```

รูป `override_authority` + `requires_full_audit` ไม่ใช่ของใหม่ — เป็นรูปเดียวกับ
`emergency.escalate` ที่ `care-authority-map.yaml:85-90` ใช้อยู่ และ `ap_policy/engine.py:233`
บังคับอยู่แล้วว่า **เพดานของ profile ยกทับ audited exception ไม่ได้**

### 2. หยุดต้องไม่รอใคร

`pause` กับ `cancel` เป็น `critical` เพราะผลกระทบจริง แต่ `override_authority: notify`
เพราะ **ความเร็วคือคุณสมบัติด้านความปลอดภัยของมัน**

หลักนี้เราเป็นคนเสนอเองที่ `dis-a84b7a8e` ว่า `tools.cancel` ต้องไม่มีวันติดคิวอนุมัติ
ไม่ว่า capability ของงานนั้นจะสูงแค่ไหน · และ agent-platform ตีพิมพ์เป็น
[ADR-0029 กฎข้อ 2](https://github.com/monthop-gmail/agent-platform/blob/main/decisions/0029-the-cost-of-not-acting.md)

> ถ้าการหยุดต้องรออนุมัติ สิ่งที่เกิดตอนต้องหยุดจริง ๆ คือมันไม่หยุด

### 3. เปิดต่อต้องไม่ง่ายกว่าหยุด — และ `resume` ห้ามเป็น `auto` เด็ดขาด

`resume` เป็น `medium` → `notify` ตาม `authority_map` · agent ทำได้ถ้า policy ของ tenant อนุญาต
แต่มีสองข้อที่ห้ามขยับ:

* **`resume` ห้ามเป็น audited exception** — ไม่มีเหตุผลด้านความเร็วมารองรับ
* **`resume` ห้ามอยู่ที่ `auto`** — ต้องมีร่องรอยว่าใครสั่งให้จอกลับมาเล่นต่อ

เสนอให้ใส่ `floor.capabilities` เพิ่มหนึ่งบรรทัดว่า `media.playback.resume: notify`
เพื่อให้ tenant ลดต่ำกว่านี้ไม่ได้ ตามรูปที่ `floor` ใช้อยู่กับ `medication.regimen.*`

### 4. ❌ ไม่ประกาศ `undoes` — และเหตุผลคือกฎข้อ 1a ของ ADR-0029 เอง

`media.playback.resume` ดูเหมือนคู่ undo ของ `pause` ที่ชัดที่สุดเท่าที่มีในระบบ
**และเราจงใจไม่ประกาศ**

กฎ 1b ผ่าน — การหยุดกับการเปิดต่อมี capability ของตัวเองแยกกัน

กฎ 1a **ไม่ผ่าน** — การเปิดต่อไม่ใช่การคืนสภาพเดิมโดยไม่มีความเสี่ยงของตัวเอง:

> ระหว่างที่จอหยุด ผู้ป่วยอาจหลับไปแล้ว · การเปิดต่อคือการปลุกคน
> ไม่ใช่การยกเลิกการหยุด · สภาพเดิมที่จะคืน **ไม่มีอยู่แล้ว**

ถ้าประกาศ กฎของ ADR-0029 จะบังคับให้ `resume` ต้องไม่ยากกว่า `pause` ซึ่งขัดข้อ 3 ของใบนี้
โดยตรง — **กฎที่ตีพิมพ์จะกลายเป็นตัวสร้างความเสียหายเอง** ซึ่งเป็นความกังวลที่
ADR-0029 เขียนกำกับไว้เองจากเคส `medication.regimen.stop` ของเรา

นี่เป็น **ผู้ผลิตรายที่สองของเคส "ดูเหมือนคู่ undo แต่ประกาศไม่ได้"** จาก repo เดียวกัน
คู่แรกคือ `medication.regimen.stop` / `medication.regimen.write`

### 5. ยังไม่เก็บพฤติกรรมการดูทีวี และนี่คือเส้นที่ทำให้ใบนี้เดินได้วันนี้

`pause` ในใบนี้ถูกสั่งจาก **งานที่ถึงกำหนด** (เตือนกินยา) หรือจาก **ผู้ดูแล** เท่านั้น
ไม่ได้ถูกสั่งจากการเฝ้าดูว่าผู้ป่วยดูทีวีนานเท่าไร

การเตือนหลังดูนาน (use case 4 ของ `dis-65f4fe3e`) ต้องเก็บข้อมูลชนิดใหม่ และชนข้อจำกัดที่
ประกาศไว้ใน `platform-contract.yaml` ว่าไม่ขยายการเก็บข้อมูลสุขภาพจนกว่า `task-4c4a109f`
จะมีคำตอบ · ใบนี้จึง **ไม่ครอบ** use case นั้น

> แยกได้สะอาดเพราะ trigger ต่างกัน ไม่ใช่เพราะ action ต่างกัน — `pause` ตัวเดียวกัน
> ใช้ได้ทั้งสองแบบ ต่างกันแค่ว่าอะไรเป็นคนสั่ง

## ทางเลือกที่พิจารณาแล้วไม่เอา

| ทางเลือก | เหตุผลที่ไม่เอา |
|---|---|
| `device.action` ตัวเดียวแล้วส่งชื่อ action เป็น parameter | เพดานจะคุมได้แค่ "แตะอุปกรณ์ได้ไหม" ไม่ใช่ "แตะอะไรได้" · `tools.deny` จะปฏิเสธทั้งก้อนหรือไม่ปฏิเสธเลย ซึ่งเป็น fail-open ที่ ADR-0026 เตือนไว้ |
| `pause` เป็น `medium` ธรรมดา | ผลกระทบไม่ใช่ medium · และการใช้ `critical` + audited exception ทำให้ **ทุกครั้งที่ใช้ถูก audit เต็ม** ซึ่งเป็นสิ่งที่เราต้องการจริง ๆ |
| `pause` ต้อง `approval_required` | ถึงเวลาต้องหยุดจริงจะไม่หยุด · ขัด ADR-0029 กฎข้อ 2 ที่เราเป็นคนเสนอ |
| ประกาศ `resume undoes pause` | ดูสมมาตรแต่ไม่จริง (ข้อ 4) · และจะบังคับให้ `resume` ง่ายกว่าที่ควร |
| ให้ endpoint หยุดเองตาม policy ที่ฝังในอุปกรณ์ | policy เป็นของโดเมน ไม่ใช่ของอุปกรณ์ · และจะไม่มี audit ฝั่งเรา ซึ่งแปลว่าไม่มีใครตอบได้ว่าจอถูกหยุดกี่ครั้ง |

## Consequences

* capability ใหม่สามตัว และเป็นครั้งแรกที่ระบบนี้มี action ที่ไม่ใช่ notify/record/propose
* `profile_check` ข้อที่ตรวจว่า `tools.allow` เป็นชุดปิดจะทำให้ **agent เรียกไม่ได้จนกว่า
  จะมีคนเพิ่มชื่อลง profile** ซึ่งเป็นพฤติกรรมที่ต้องการ ไม่ต้องทำอะไรเพิ่ม
* ต้องมีที่เก็บว่า "ตอนนี้จอถูกหยุดโดยเราอยู่ไหม" ไม่งั้น `resume` จะเปิดสิ่งที่เราไม่ได้หยุด
  — เป็น state ของ endpoint ไม่ใช่ของโดเมน แต่โดเมนต้องมีตัวชี้ไปถึง
* **ยังไม่ implement** — ใบนี้ตัดสินรูปกับระดับความเสี่ยง · ตัวกลไกเป็นงานถัดไป
  และต้องมาพร้อม conformance check ที่บังคับข้อ 3 กับข้อ 4 ได้จริง
