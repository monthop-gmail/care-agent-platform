# ADR-0011: audit เก็บ "ตัวชี้" ไม่ใช่ "เนื้อหา" — `attributes` เป็นชุดปิดที่ประกาศไว้

**Status:** Accepted (2026-09-11)
**Depends on:** [ADR-0004](0004-care-event-vocabulary.md) · [ADR-0006](0006-ai-has-no-medical-authority.md) · [ADR-0007](0007-consent-and-data-access.md)

## Context

`event/v1` นิยาม `metadata` (ที่เราเรียกว่า `attributes`) ไว้ว่า

```yaml
metadata:
  type: object
  description: 🔒 invariant — ห้ามเก็บ private reasoning หรือ chain-of-thought เป็น audit record
```

คือ **เปิดทั้งหมด** มีข้อห้ามข้อเดียวและเป็นข้อที่ตรวจด้วย denylist สี่คำ
เราทำตามข้อนั้นครบมาตลอด และนั่นทำให้เชื่อไปเองว่าช่องนี้ถูกดูแลอยู่

agent-platform ตกลงกับเราไว้ใน `dis-65134078` ว่าจะเปิด RFC เรื่อง event payload
ที่ต้นทาง `devfactory-core` โดย **รอผลของการปิด `attributes` ฝั่งเราก่อน** —
เหตุผลที่เขาให้คือระบบที่มี event 40+ ชนิดรันอยู่จริงจะเจอของที่ไม่มีใครคาด
และ RFC ควรได้ข้อมูลนั้นก่อนตีพิมพ์ · ใบนี้คือผลนั้น

### สิ่งที่เจอตอนไล่ปิดจริง

ไม่ใช่ช่องว่างเชิงทฤษฎี — เราเก็บของพวกนี้ลง audit อยู่จริงในวันที่เขียนใบนี้

| ที่ | สิ่งที่อยู่ใน audit | ทำไมถึงเป็นปัญหา |
|---|---|---|
| `care_medication.propose_version` | `name` = ชื่อยา คู่กับ `patient_id` | ชื่อยา + คนที่ระบุตัวได้ = ข้อมูลสุขภาพ ไม่ใช่ metadata |
| `care_medication.detect_conflicts` | `**detail` กาง dict ทั้งก้อน — ชื่อยา ตารางกินยา ชื่อผู้สั่ง | open bag ซ้อนใน open bag · ไม่มีใครทบทวนตอนเพิ่มคีย์ |
| `care_escalation._send_reminder` | `text` = ข้อความที่ส่งให้ผู้ป่วย **ทั้งประโยค** | ข้อความ interpolate `job.label` เข้าไป (เช่นชื่อยา) |
| `ap_approval.request/decide/withdraw` | `summary` และ `reason` ที่ **คนพิมพ์** | ข้อความอิสระของมนุษย์ ไม่มีใครรู้ว่ามีอะไรอยู่ในนั้น |
| `care_appointment.add` | `specialty` + `purpose` คู่กับ `patient_id` | ไปหาหมอแผนกอะไร เป็นข้อมูลสุขภาพเช่นกัน |
| `care_careplan.set_status` | เหตุผลที่ผู้ดูแลพิมพ์ ถูกก๊อปลง trail ของ **ทุก job ที่ถูกยกเลิก** | คนที่อ่าน trail ของงานได้ ไม่จำเป็นต้องอ่านเหตุผลนั้นได้ |

ทุกตัวมี row ของโดเมนอยู่แล้ว และ event มี `subject_id` ชี้ไปถึง row นั้นอยู่แล้ว
การก๊อปเนื้อหามาไว้ใน audit จึงไม่ได้เพิ่มความสามารถในการตรวจสอบเลย
แต่สร้างที่เก็บ PII ขึ้นมาอีกที่หนึ่ง — **ที่ที่ลบไม่ได้** เพราะ audit เป็น append-only
และเป็นที่ที่สิทธิ์ในการอ่านไม่ได้ผูกกับ consent แบบเดียวกับตารางของโดเมน

## Decision

### 1. `attributes` เป็นชุดปิด ประกาศที่ `care_addons/ap_audit/attributes.py`

คีย์ที่ไม่ได้ประกาศ → `emit()` reject · เพิ่มคีย์ใหม่ = ต้องมาเขียนบรรทัดในทะเบียน
ซึ่งเป็นจุดเดียวที่บังคับให้คนเขียนตอบว่า **ค่านี้เป็นตัวชี้หรือเป็นเนื้อหา**

### 2. ทุกคีย์มี "ชนิด" และไม่มีชนิดสำหรับข้อความเสรี

`id` · `id_list` · `ref` · `code` · `code_list` · `count` · `number` · `time` · `flag` · `flag_map`

ไม่มีชนิดไหนรับประโยคของมนุษย์ได้ · `code` บังคับว่าต้องเป็น **token ASCII**
ไม่ใช่แค่ "ห้ามมีช่องว่าง" เพราะภาษาไทยเขียนติดกัน ประโยคเต็มประโยคจึงผ่านกฎห้ามเว้นวรรคได้สบาย
(เจอตอนเขียนเทสข้อนี้ ไม่ใช่ตอนออกแบบ)

### 3. ข้อยกเว้นมีคีย์เดียว และตั้งชื่อให้ผิดยาก

`policy_reason` (`system_text`) — ประโยคที่ `ap_policy` สร้างเองจาก `authority_map` + profile
ไม่มีค่าจาก record ของผู้ป่วยและไม่มีค่าที่ผู้ใช้พิมพ์

🔒 จงใจ **ไม่** ใช้ชื่อ `reason` เพราะ `reason` เป็นชื่อที่ใครก็หยิบไปใส่ข้อความของคนได้
โดยไม่รู้ตัว — และเราเคยทำมาแล้วสามที่

### 4. บังคับสามชั้น

| ชั้น | จับอะไร |
|---|---|
| `emit()` | ทุก event ที่ระบบผลิตจริง รวมทั้งที่มาจาก `**spread` |
| `tests/test_audit_attributes.py` (AST scan) | คีย์ที่มีคนเขียนไว้ใน `care_addons/` **แม้เทสไม่ได้เดินผ่าน path นั้น** |
| `conformance/payload_check.py` | payload ที่ผลิตจริง 112 ใบ — ให้ผู้ตรวจภายนอกเห็นว่าถูกบังคับจริง ไม่ใช่แค่มี unit test |

### 5. กฎอยู่ในโค้ด ไม่ได้อยู่ใน JSON Schema — โดยตั้งใจ

เขียน `propertyNames.enum` 80 คีย์ลง `care-event.schema.yaml` ได้ และมันจะดูเป็นทางการกว่า
แต่ schema เขียนได้แค่ว่า *คีย์ไหนมีได้* · เขียนไม่ได้ว่า **ใครเป็นคนเขียนค่านั้น**
ซึ่งเป็นแกนจริงของกฎนี้ (`policy_reason` กับ `summary` เป็น string เหมือนกันทุกประการ)
และรายการที่ต้องซิงก์สองที่จะ drift ภายในเดือนเดียว

## สิ่งที่ใบนี้ **ไม่ได้** ปิด — และต้องพูดให้ตรง

> **Addendum (2026-09-11)** — ตอนเขียนใบนี้เรารวม `transition.reason` กับ `error.message`
> ไว้เป็นก้อนเดียวว่า "รอ RFC" · `agent-platform` เปิดไฟล์ตรวจแล้วชี้ว่าสถานะสองฟิลด์
> **ไม่เหมือนกันเลย** (`dis-65134078` `seq 26`) — `error/v1` `message` **มีกฎอยู่แล้ว**
> ในสัญญาว่าห้ามใส่ credential / PII / เนื้อหา prompt · ส่วน `transition.reason` เป็น
> `type: string` เปล่า ๆ ไม่มีข้อจำกัดสักบรรทัด
>
> แปลว่าข้อแรกเป็นของที่เราตรวจได้เองทันทีและถ้าผิดคือ**ผิดสัญญาที่ pin อยู่แล้ววันนี้**
> ไม่ใช่เรื่องที่รอกติกาใหม่ · เราตรวจแล้ว: `error.message` หนึ่งที่วางข้อความดิบจาก
> ช่องทางส่ง (รวม `str(e)` ของ exception ใด ๆ ที่ sender โยนออกมา ซึ่งอาจมีตัวข้อความ
> ที่กำลังส่งอยู่ในนั้น) — แก้แล้ว ข้อความดิบอยู่ที่ `care_notification.delivery_error`
> ตามเดิม และ `error.details` ชี้ด้วย `notification_id`
>
> และพบช่องที่สามระหว่างทาง: `error/v1` นิยาม `details` ว่า `{"type": "object"}`
> คือ open bag รูปเดียวกับ `metadata` เป๊ะ ต่างกันแค่ไม่มีใครพูดถึงมัน — ปิดด้วยทะเบียน
> เดียวกันแล้ว
>
> สิ่งที่ยังรอ RFC จริง ๆ จึงเหลือ **`transition.reason` ที่เดียว**

`transition.reason` เป็นฟิลด์ข้อความที่ `event/v1` นิยามเอง อยู่นอกกล่องนี้

เหตุผลที่ผู้ดูแลพิมพ์ตอนหยุดคำสั่งของหมอ **ยังอยู่ใน audit** ที่ `transition.reason`
และย้ายออกไม่ได้ เพราะ [ADR-0006](0006-ai-has-no-medical-authority.md) บังคับว่าต้องตอบให้ได้ว่า
คำสั่งของหมอถูกหยุดเพราะอะไร และ `care_careplan_task` ไม่ได้เก็บข้อความนั้นไว้บนแถว

> สิ่งที่เราแก้ได้คือ **หยุดก๊อปมันไปที่อื่น** — เดิมประโยคนั้นถูกส่งต่อไปเป็น
> `transition.reason` ของทุก job ที่ถูกยกเลิกตามคำสั่งนั้น ตอนนี้อยู่ที่ event เดียว

**ข้อนี้คือของที่ RFC ต้องตอบ ไม่ใช่ของที่ consumer ตอบเองได้:** ข้อกำหนด
"audit ห้ามถือ PII ของ subject" ชนกับข้อกำหนด "ต้องตอบได้ว่าทำไมถึงหยุดการรักษา"
ที่ฟิลด์เดียวกัน · กฎที่บอกแค่ว่า "ห้ามมี PII" จะทำให้ระบบที่ทำถูกกลายเป็นระบบที่ conform ไม่ได้
สิ่งที่ต้องมีคือกฎว่า **ฟิลด์ไหนถือข้อความของมนุษย์ได้** และกติกาของการเก็บ/ลบที่ฟิลด์นั้น

## Consequences

* audit trail อ่านแล้ว "จืด" ลงมาก — ตั้งใจ · ผู้อ่านที่ต้องการเนื้อหาต้องไปอ่าน row จริง
  ซึ่งผ่าน consent · คนที่อ่านได้แค่ trail จะไม่ได้ชื่อยาของผู้ป่วยไปฟรี ๆ อีกต่อไป
* `_settle()` ไม่รับ `reason` อีกแล้ว — `settled_as` ตอบว่า trail จบแบบไหน และ
  `STATE_TRANSITION` ก่อนหน้าเก็บเหตุผลไว้ครบ
* event เก่าที่บันทึกไปแล้วยังมีเนื้อหาเดิมอยู่ · audit เป็น append-only จึงลบย้อนหลังไม่ได้
  **นี่คือราคาที่จ่ายไปแล้วของการเปิดช่องนี้ไว้ตั้งแต่แรก** และเป็นเหตุผลที่ข้อจำกัดแบบนี้
  ต้องมาตั้งแต่ก่อนมี production data ไม่ใช่หลัง
* ถ้า agent-platform ตัดสินใจปิด `metadata` ที่ระดับ contract เราจะต้องแปลงทะเบียนนี้
  ให้เป็นรูปที่เขากำหนด — ซึ่งง่าย เพราะมันเป็นตารางเดียวอยู่แล้ว
