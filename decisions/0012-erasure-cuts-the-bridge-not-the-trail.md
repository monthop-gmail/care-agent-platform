# ADR-0012: สิทธิขอลบข้อมูล — erasure ตัด "สะพานไปหาตัวตน" ไม่ใช่ลบ trail

**Status:** Accepted (2026-09-12)
**Depends on:** [ADR-0007](0007-consent-and-data-access.md) · [ADR-0011](0011-audit-holds-pointers-not-content.md) · [ADR-0006](0006-ai-has-no-medical-authority.md)
**Implements:** `dec-d1302f96` (pstack · เจ้าของงานอนุมัติ 2026-09-10) — ทางเลือก **A pseudonymization**

## Context

`architecture/patient-lifecycle.md` §5 เขียนไว้ตั้งแต่ต้นว่า

> ถอน consent · ปิด care profile · ลบข้อมูลตาม PDPA
> — **audit event ลบไม่ได้** (append-only) แต่ต้องลบข้อมูลส่วนบุคคลที่อ้างถึงได้
> วิธีจัดการเรื่องนี้ต้องมี ADR แยกก่อนถึง M6

ใบนี้คือ ADR นั้น และมันมาช้ากว่าที่ควร — เราประกาศใน `platform-contract.yaml`
ไปแล้วว่ากลไกนี้ยังไม่มี ซึ่งเป็นคำแถลงที่จริงแต่ไม่ใช่คำตอบ

ระดับ ecosystem เคาะไปแล้วที่ `dec-d1302f96`: **ทางเลือก A — pseudonymization ตั้งแต่ต้นทาง**
(B crypto-shredding เป็นชั้นเก็บของตาราง mapping ทีหลังได้ · C tombstone ถูกปฏิเสธ
เพราะการแก้ field ใน row ที่ควร immutable ทำลาย time-frozen evaluation — ระบบจะยังตอบ
ทุกคำถามได้เหมือนเดิม แค่ตอบผิด และไม่ล้มเหลวแบบมีเสียง)

ใบนั้นผูกเงื่อนไขสามข้อไว้กับ A และระบุว่า **ไม่ใช่ของเสริม**:

1. **data minimization เป็นเงื่อนไขที่ทำให้ A มีความหมาย** — A ตัดสะพานเส้นเดียว
   ถ้าโดเมนเขียนตัวตนลงอีกหลายที่ การตัดสะพานนั้นไม่เปลี่ยนอะไร
   > ใบอ้างหลักฐานจาก repo นี้โดยตรง: *"care ยืนยันด้วยของจริงว่า audit ของโดเมนถือคำพูด
   > ผู้ป่วย พิกัด GPS ชื่อยา และ LINE binding อยู่"*
2. **ต้องเคาะคู่กันว่า audit เก็บ payload อะไรได้บ้าง** — ตัดสินทีหลังไม่ได้
3. **erasure ห้ามเดินทางเดียวกับ revoke consent** — เป็นการกระทำคนละอย่างและมีผลทาง
   กฎหมายคนละแบบ · ถ้า implement ทับกัน บันทึกจะบอกว่าเจ้าของข้อมูลถอนความยินยอม
   ทั้งที่เขาขอให้ลบตัวตน และตรวจย้อนไม่เจอเพราะบันทึกดูปกติ

ข้อ 1 กับข้อ 2 คือ [ADR-0011](0011-audit-holds-pointers-not-content.md) ซึ่งทำไปแล้ว
ใบนี้ตอบข้อ 3 และปิดช่องสุดท้ายของข้อ 1

## สิ่งที่พบตอนไล่ให้ครบ — `attributes` ไม่ใช่ช่องเดียว

ADR-0011 ปิด `metadata` · `error.details` · `actor.display_name` แต่ `transition.reason`
ถูกทิ้งไว้พร้อมคำอธิบายว่า "ย้ายออกไม่ได้เพราะ ADR-0006 บังคับให้ตอบได้ว่าหยุดคำสั่งเพราะอะไร
และแถวไม่ได้เก็บประโยคนั้นไว้"

พอไล่จริงเพื่อเขียนใบนี้ พบว่าคำอธิบายนั้น **ไม่ครบและไม่ถูก**

| ทาง | ใครเขียนค่า | มีที่เก็บบนแถวอยู่แล้วไหม |
|---|---|---|
| `ap_consent.revoke` | คน | ✅ `revoked_reason` |
| `care_careplan.set_status` | คน | ❌ ไม่มี |
| `care_medication.propose / confirm / stop` | คน (เหตุผลเชิงคลินิก) | ✅ `version.reason` |
| `care_inventory.close_item` | คน | ❌ ไม่มี |
| `care_organization.end_membership` | คน | ✅ `ended_reason` |
| `care_safety.acknowledge / close_event` | คน (โน้ตเรื่องการล้ม) | ✅ `resolution_note` |
| `care_orientation` (คำถามเรื่องแผน) | **ผู้ป่วย** — คำถามที่เขาพิมพ์เอง ทั้งประโยค | ❌ ไม่มี |

**แปดทาง ไม่ใช่ทางเดียว** และหกในแปดมีที่เก็บบนแถวอยู่แล้ว — audit ถือสำเนาไว้เฉย ๆ

> ⚠️ เราเคยประกาศใน `platform-contract.yaml` ว่า *"มีเส้นทางเดียวที่เป็นข้อความที่คนพิมพ์"*
> และรายงานแบบนั้นกับ agent-platform ไปแล้ว · **ใบประกาศนั้นไม่ตรงกับของจริง** —
> ซึ่งเป็นความล้มเหลวแบบเดียวกับที่เราเตือนเขาเองว่า *"ใบที่ไม่ตรงกับของจริงคือใบที่ทำให้คนเลิกตรวจ"*
>
> สาเหตุไม่ใช่ความเลินเล่อ: ตัวตรวจ leaf บอกได้ว่า **leaf ไหน** ไม่ใช่ตัวชี้ แต่บอกไม่ได้ว่า
> **ใครเป็นคนเขียนค่า** ตอนประกาศจึงเหลือเป็นการอ่านโค้ดด้วยตา และเราอ่านไม่ครบ
> นี่คือข้อจำกัดที่ RFC-0013 เขียนไว้เองว่ากฎนี้บังคับได้ที่ผู้ผลิตเท่านั้น — เจอกับตัวแล้ว

## Decision

### 1. erasure = ลบแถวของโดเมน · audit อยู่ต่อ · สะพานไปหาตัวตนถูกตัด

ทางเลือก A ตาม `dec-d1302f96` · หลังลบ trail ยังตอบได้ว่า **เกิดอะไรขึ้นเมื่อไร**
แต่ตอบไม่ได้ว่า **ของใคร** เพราะแถวที่แปลง `patient_id` เป็นคนถูกลบไปแล้ว

ข้อนี้ใช้ได้ก็ต่อเมื่อ audit ไม่ถือเนื้อหา — ซึ่งเป็นเหตุผลที่ ADR-0011 ต้องมาก่อนใบนี้

### 2. `transition.reason` เป็นข้อความที่ **โค้ดเราสร้างเอง** เท่านั้น

ทั้งแปดทางย้ายแล้ว · ที่ยังไม่มีที่เก็บบนแถว เพิ่มคอลัมน์ให้
(`care_careplan_task.status_reason` · `care_inventory_item.close_reason`)
ส่วนคำถามที่ผู้ป่วยพิมพ์ **ไม่เก็บเลย** เพราะไม่มี ADR ข้อไหนต้องการมัน

บังคับด้วย `REASON_INTERPOLATIONS` ใน `ap_audit/attributes.py` + AST scan ใน CI:
ชื่อที่แทรกเข้าไปใน `reason` ต้องประกาศไว้พร้อมเหตุผลว่าทำไมมันไม่ใช่ข้อความเสรี

> 🔒 ตัวตรวจบอกได้แค่ว่าชื่อไหนถูกแทรก ไม่ได้บอกว่าค่าข้างในมาจากใคร
> ทะเบียนจึงเป็นคำตอบของ**คน** และนั่นคือที่ที่ความผิดพลาดข้างบนจะถูกจับได้ครั้งหน้า

**ADR-0006 ยังถูกรักษาไว้ครบ** — คำถามว่า "ทำไมคำสั่งของหมอถูกหยุด" ยังตอบได้
จากแถวที่ `subject_id` ชี้ถึง ต่างกันตรงที่คำตอบนั้นอยู่ใต้ consent และ **ลบได้**
ส่วน audit ยังบันทึกตลอดไปว่า *มีการหยุด ใครหยุด เมื่อไร*

### 3. erasure เป็นการกระทำคนละอย่างกับ revoke consent — ห้ามใช้ทางเดียวกัน

เงื่อนไขข้อ 3 ของ `dec-d1302f96` · แยกทั้ง capability · event · และใบบันทึก
ระบบต้องไม่มีทางที่ "ขอให้ลบ" ถูกบันทึกเป็น "ถอนความยินยอม" หรือกลับกัน

### 4. สิ่งที่ลบไม่ได้ ต้องประกาศ ไม่ใช่ปล่อยให้เข้าใจเอง

`platform-contract.yaml` `cutover` ระบุไว้แล้วว่า event ที่เขียนก่อนจุด cutover
ยังมีชื่อยา ข้อความเตือน ชื่อคน และประโยคที่คนพิมพ์อยู่ · `remediation: ไม่มี`

## สิ่งที่ใบนี้ยัง **ไม่ได้** ทำ

* **ยังไม่มีกลไก `erase_patient()`** — ใบนี้ตัดสินรูปและปิดเงื่อนไขที่ทำให้รูปนั้นมีความหมาย
  ตัวกลไกเป็นงานถัดไป และต้องเป็น capability ที่ `action_risk: critical` + ต้องมีคนสั่ง
  ไม่มีวัน autonomous
* **คำถามทางกฎหมายยังเปิดอยู่** — `dec-d1302f96` ระบุไว้เองว่ายังไม่มีใครถามคนรู้กฎหมายว่า
  audit trail เข้าข่ายข้อยกเว้นเรื่องฐานการเก็บหรือไม่ · ถ้าเข้าข่าย คำถามทั้งใบเปลี่ยนรูป
  **ผู้เขียนใบนี้ไม่ใช่นักกฎหมาย และใบนี้ไม่ใช่คำแนะนำทางกฎหมาย**

## Consequences

* audit trail จืดลงอีกชั้น — `transition.reason` เหลือเป็นคำบรรยายเชิงกลไก
  ผู้อ่านที่ต้องการเหตุผลของคนต้องไปอ่านแถว ซึ่งผ่าน consent และหายไปเมื่อถูกลบ
* `cancel_jobs()` ไม่รับ `reason` จากผู้เรียกอีกแล้ว — ประโยคของคนไหลผ่านมาทางนั้นไม่ได้
  โดยโครงสร้าง ไม่ใช่โดยกติกา
* ผู้ป่วยที่ถามคำถามกับระบบ ไม่มีคำถามของตัวเองค้างอยู่ใน audit อีก
* **ราคาที่จ่าย:** event ที่เขียนไปแล้วยังมีของเดิมครบ · ทุกอย่างในใบนี้มีผลกับใบที่เขียน
  หลังจากนี้เท่านั้น ซึ่งเป็นรูปเดียวกับ ADR-0011 และเป็นเหตุผลเดียวกันว่าทำไม
  ข้อจำกัดแบบนี้ต้องมาก่อนมี production data
