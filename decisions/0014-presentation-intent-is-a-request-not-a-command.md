# ADR-0014: presentation intent เป็น "คำขอ" ไม่ใช่ "คำสั่ง" — และไม่มีสถานะไหนกลายเป็นหลักฐานเอง

**Status:** Accepted (2026-09-27)
**Depends on:** [ADR-0006](0006-ai-has-no-medical-authority.md) · [ADR-0008](0008-patient-channel-is-deterministic.md) · [ADR-0011](0011-audit-holds-pointers-not-content.md)
**ตอบ:** `task-7538109a` ADR A · ต่อจาก [`architecture/care-endpoints.md`](../architecture/care-endpoints.md)

## Context

`CareNotification.text` เป็นข้อความเดียว (`care_escalation/models.py:60`) ไม่มีที่บอกว่า
แสดงแบบ overlay หรือเต็มจอ · ต้องอ่านออกเสียงไหม · ต้องรอคนกดตอบไหม · ค้างบนจอได้นานแค่ไหน

วันนี้ไม่เป็นปัญหาเพราะช่องทางเดียวที่มีคือ LINE ซึ่งเป็นข้อความล้วน · endpoint ที่มีหน้าจอ
และลำโพงทำให้คำถามนี้มีคำตอบที่ต่างกันได้จริง และคำตอบที่ผิดมีราคา —
overlay เต็มจอตอนตีสามไม่ใช่ปัญหาด้านสุนทรียะ

## Decision

### 1. presentation intent เป็นฟิลด์เชิงโครงสร้าง แยกจาก `text` เสมอ

ห้ามฝัง markup หรือคำสั่งการแสดงลงในข้อความ · เหตุผลไม่ใช่ความสะอาด: `text` คือสิ่งที่
**ผู้ป่วยได้อ่าน** และเป็นของที่ต้องตรวจย้อนหลังได้ว่าเราพูดอะไรไป — ถ้ามี markup ปนอยู่
สิ่งที่บันทึกไว้จะไม่ใช่สิ่งที่เขาเห็น

ทุกค่าใน intent เป็น **code จาก vocabulary ปิด** ไม่ใช่ข้อความเสรี ตาม [ADR-0011](0011-audit-holds-pointers-not-content.md)
— เพราะ intent จะไปโผล่ใน audit และ audit เก็บตัวชี้ ไม่ใช่เนื้อหา

### 2. intent เป็น **เพดานที่ขอ** ไม่ใช่สิ่งที่ได้

policy + `severity` + quiet hours เป็นผู้ตัดสินว่าจริง ๆ แล้วแสดงแบบไหน
`care_escalation/policy.py:41` กับ `services.py:93` มีกลไกนี้อยู่แล้วและใช้กับ LINE อยู่

> ขอ `full_screen` + `tts` ตอนตีสามสำหรับงาน `severity: low` แล้วได้ **เงียบไว้จนเช้า**
> เป็นพฤติกรรมที่ถูก ไม่ใช่ bug

รูปนี้เหมือน profile ที่เป็นเพดานของ agent — **ค่าที่กว้างที่สุดชนะไม่ได้**

### 3. สี่สถานะ และเราบันทึกได้แค่สาม

```text
delivered      ช่องทางรับไปแล้ว            ← มีอยู่แล้ว: delivery_status = sent
presented      endpoint วางบนจอจริง        ← ใหม่ · endpoint รายงาน
seen           มีคนอยู่หน้าจอและมองเห็น     ← ❌ บันทึกไม่ได้ ดูข้อ 4
acknowledged   คนกดปุ่มตอบ                 ← มีอยู่แล้ว: acknowledge() + patient_confirmed
```

### 4. `seen` ประกาศไม่ได้ และนี่เป็นการตัดสินใจ ไม่ใช่ข้อจำกัดชั่วคราว

TV บอกได้ว่าจอเปิดอยู่ · แอปอยู่หน้าไหน · เสียงดังเท่าไร · **บอกไม่ได้ว่ามีใครมองอยู่**

การจะรู้ต้องมีกล้องหรือเซ็นเซอร์ตรวจการมีอยู่ของคน ซึ่งเป็น **การเก็บข้อมูลชนิดใหม่**
ที่ชนข้อจำกัดที่ repo นี้ประกาศไว้เอง (`task-4c4a109f` ยัง blocked)

และถ้าเดาแทน — เช่นถือว่า "จอเปิด + overlay แสดง 30 วินาที = เห็นแล้ว" — ระบบจะได้สถานะ
ที่**ตอบได้ทุกคำถามเหมือนเดิม แค่ตอบผิด** ซึ่งเป็นรูปความล้มเหลวที่ `dec-d1302f96`
ใช้เป็นเหตุผลปฏิเสธทางเลือก C

> ถ้าวันหนึ่งมีเซ็นเซอร์จริงและมีคำตอบทางกฎหมายแล้ว `seen` เพิ่มได้แบบ additive
> สิ่งที่ใบนี้ห้ามคือ **การอนุมานมันขึ้นมาจากของที่เรามี**

### 5. ไม่มีสถานะไหนกลายเป็น evidence เอง

`delivered` และ `presented` เป็นข้อเท็จจริงเกี่ยวกับ **ช่องทาง** ไม่ใช่เกี่ยวกับ **คน**
ทางเดียวที่งานปิดได้ยังเป็น `acknowledge()` ที่มี `evidence.kind` ของคนเท่านั้น

ข้อนี้ต่อยอดจาก [ADR-0006 ข้อ 5](0006-ai-has-no-medical-authority.md) ตรง ๆ:
ไม่มีหลักฐาน = ตอบว่าไม่มีหลักฐาน · **"แสดงบนจอแล้ว" ไม่ใช่หลักฐานว่ากินยาแล้ว**

บังคับด้วย AST scan แบบเดียวกับที่ใช้กับ `transition.reason` —
ค่าใน `evidence.kind` ต้องมาจากชุดปิดที่ประกาศไว้ และห้ามมี code path ใดแปลง
`delivery_status` หรือ `presentation_state` เป็น `evidence`

### 6. ตัวเลือกที่ผู้ป่วยกดได้เป็นชุดปิด — endpoint คิดเพิ่มเองไม่ได้

[ADR-0008](0008-patient-channel-is-deterministic.md) บังคับว่าช่องทางของผู้ป่วยตอบด้วย
intent router ที่กำหนดไว้ล่วงหน้าเท่านั้น · รีโมทมีปุ่มจำกัดจำนวน ซึ่งทำให้ข้อนี้
**ง่ายกว่า LINE** เพราะไม่มีช่องให้พิมพ์อิสระตั้งแต่ต้น

ชุดที่เสนอ map ตรงไปยังของที่มีอยู่แล้ว:

| ปุ่ม | เรียกอะไร | ผล |
|---|---|---|
| ทำแล้ว | `acknowledge(done=True)` | `confirmed` · ปิดงาน |
| ยังไม่ได้ทำ | `acknowledge(done=False)` | `acknowledged` · ตั้ง backoff ต่อ (มีอยู่แล้วที่ `services.py:702`) |
| ขอความช่วยเหลือ | `caregiver.notify` | แจ้งผู้ดูแล — capability ที่มีอยู่ |

**ไม่มีปุ่ม "ปิด/ไม่สนใจ"** เพราะการปิดข้อความเตือนยาโดยไม่มีสถานะ คือการทำให้งานหายไป
เงียบ ๆ ซึ่งขัด `no silent state change` ที่เรา pin ไว้เป็น frozen guarantee

## รูปของฟิลด์ที่เสนอ

```yaml
presentation:            # ทุกค่าเป็น code จาก vocabulary ปิด
  surface: overlay | full_screen | ambient      # ขอ ไม่ใช่ได้
  speak: true | false                          # TTS
  response: required | optional | none
  dwell: short | medium | until_answered        # ไม่ใช่วินาที — วินาทีเป็นเรื่องของ endpoint
```

`dwell` เป็น code ไม่ใช่ตัวเลข โดยเจตนา — "30 วินาที" บนจอ 55 นิ้วกับบนแท็บเล็ตไม่ใช่
ประสบการณ์เดียวกัน การตัดสินใจนั้นเป็นของ endpoint ส่วนโดเมนบอกแค่ว่า "สั้น" หรือ
"จนกว่าจะตอบ"

## ทางเลือกที่พิจารณาแล้วไม่เอา

| ทางเลือก | เหตุผลที่ไม่เอา |
|---|---|
| ฝัง markup ลง `text` (`<overlay>…`) | `text` คือสิ่งที่ผู้ป่วยได้อ่าน ต้องตรวจย้อนได้ว่าเราพูดอะไร · และ markup จะกลายเป็นข้อความเสรีใน audit ซึ่ง ADR-0011 ห้าม |
| ให้ endpoint ตัดสิน surface เองทั้งหมด | quiet hours กับ severity เป็นกติกาของ **การดูแล** ไม่ใช่ของอุปกรณ์ · ถ้าอยู่ฝั่ง endpoint ทุกยี่ห้อต้อง implement ใหม่และจะไม่ตรงกัน |
| `dwell` เป็นวินาที | ผูกโดเมนกับสมมติฐานเรื่องขนาดจอและระยะการมอง |
| เพิ่ม `seen` โดยอนุมานจาก uptime ของจอ | ได้สถานะที่ตอบผิดอย่างมั่นใจ · รูปเดียวกับที่ `dec-d1302f96` ปฏิเสธทางเลือก C |
| ให้ `presented` ปิดงานได้เมื่อ `severity: low` | เป็นการเปิดช่องให้ delivery กลายเป็น evidence ทีละนิด · ข้อ 5 จึงเขียนเป็น "ไม่มีสถานะไหน" ไม่ใช่ "ส่วนใหญ่ไม่" |

## ผลต่อของที่มีอยู่

* **LINE ไม่กระทบ** — `presentation` เป็น optional · sender ที่ไม่รู้จักฟิลด์นี้ทำงานเหมือนเดิม
  (`register_sender` ส่ง `notification` ทั้งก้อนให้ sender อยู่แล้ว · `care_line/outbound.py:20`
  อ่านแค่ `text` กับ `channel`)
* **precondition หนึ่งข้อ** — `care_patient.channels` ต้องเป็น vocabulary ปิดก่อน
  (`models.py:36` วันนี้เป็น `JSON` list ที่รับอะไรก็ได้) ไม่งั้นช่องทางที่สะกดผิดจะเงียบ
* `presentation` ต้องมีที่อยู่ใน `attributes` registry ถ้าจะโผล่ใน audit — และเพราะทุกค่า
  เป็น code มันจะผ่านกฎของ ADR-0011 ได้โดยไม่ต้องยกเว้นอะไร
